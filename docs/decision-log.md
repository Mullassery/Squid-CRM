| D-007 | Accepted (owner) | Phase 4 vertical slice = **Person + auth + workspace bootstrap** (sign-in and workspace provisioning so the real frontend can log in against Rust). | Faster end-to-end validation than object-only slice. | Phase 4 scope expanded accordingly. |

| D-008 | Accepted | Session tokens are opaque 32-byte values stored only as SHA-256 hashes; access tokens are HS256 JWTs with `typ`, `sid` and `jti` claims; refresh tokens are opaque, hashed and rotated. | Prevent login-token replay and token theft from DB dumps. | Access tokens are checked against a live session; signout deletes the session and revokes refresh tokens. |
| D-009 | Superseded | The Phase 4 slice uses `limit`/`offset` pagination and returns `pageInfo` with `null` cursors. | Fastest path to a testable slice. | **Temporary divergence**: cursor pagination is required before parity; tracked in TODO. |
| D-010 | Accepted | Integration tests run against real PostgreSQL 16; CI uses a Postgres service container. | Docker was unresponsive locally, so PostgreSQL 16 was installed via Homebrew for development. | Tests are not skipped when a DB is absent — `TEST_DATABASE_URL` is required and the suite fails clearly if unset. |

| D-011 | Superseded by D-014 | Capture golden contracts from `twentycrm/twenty:v2.49.0` (the newest published image) rather than 2.50.0. | A live oracle is more valuable than source-derived guesses, and no 2.50.0 image exists. | Fixtures are one release behind the audited source; re-capture at 2.50.0 or capture from a source build. |
| D-012 | Superseded by D-016 | Treat API keys as the required credential for the upstream data API and record the current bearer/cookie acceptance as a **deliberate divergence**. | The frontend integration is the long-term target; being more permissive now kept the early slice testable. | Superseded once the data API rejected user access tokens. |
| D-013 | Accepted | Reproduce the explicit `activateWorkspace` step in the workspace lifecycle. | The data schema does not exist until activation; the slice's atomic bootstrap is a simplification, not the contract. | Signup semantics differ until the lifecycle is split into create → activate. |
| D-014 | Accepted | Capture golden contracts from a locally built image at the pinned source (`08a0e5f1`, 2.50.0) and treat `contracts/v2.50.0/` as authoritative. | No 2.50.0 Docker Hub tag exists; a source build is reproducible and matches the audited commit. | Diff vs v2.49.0 recorded; v2.49.0 retained only for comparison. |
| D-015 | Accepted | Map frontend operations and REST routes from the generated Apollo documents and captured OpenAPI into committed reports (`docs/frontend-operation-map.md`, `docs/rest-route-map.md`) produced by scripts. | Phase 2 requires every operation/route to be traceable, and hand-maintained lists drift. | Regenerate after schema or router changes; reports distinguish schema-level coverage from runtime parity. |
| D-016 | Accepted | The data API (`/graphql`, `/rest`) accepts API keys or the session cookie, never user access tokens; `/metadata` accepts access tokens. Refresh tokens are opaque, rotated on use and replay-safe; signout revokes the session. Add an Origin check for unsafe cookie-authenticated requests and a 10/15-minute in-process auth burst limiter. | Upstream rejects access tokens on data APIs and rotates app tokens. | Tests cover token rotation/replay, signout revocation, foreign-origin rejection and API-key-only data access. Edge/multi-replica deployments should add distributed rate limiting. |
| D-017 | Accepted | Implement REST `fields` projection and `depth` validation for the five standard objects; include `id` in every projection and preserve upstream error text for unknown fields/depths. | Captured v2.50.0 fixtures show `depth` is 0/1 and `fields` accepts top-level names only. | GraphQL projections use selection sets; `viewId`/groupBy remains open. |
| D-018 | Accepted | Model `avatarFile` as `Option<Vec<FileObject>>` and parse stored JSONB as file objects. | Captured schema exposes `[FileObject]` (or null). | Writes still require file storage/upload wiring; reads match the contract. |
| D-019 | Accepted | Implement REST `groupBy` in memory for the seven standard object slices; store uploaded files in `core.files` and persist metadata indexes in `core.index_metadata`/`core.index_field_metadata`. Expose built-in role and permission-flag queries. | Phase 4 follow-ups require `viewId`/groupBy, `avatarFile` writes and index/role metadata; a full dynamic schema and object-storage backend do not fit this increment. | GroupBy semantics match captured fixtures (bare array, string aggregates, null-last groups, date buckets). Upload URLs are UUID-addressed and unauthenticated until storage signing lands. Index rows do not create physical indexes; relation/morph metadata and the role enforcement engine remain open. |
| D-020 | Accepted | Derive `Object.searchFieldMetadataList` from searchable fields plus the object's tsvector field, and populate `Field.relation` for seeded forward relation fields. Reverse targets use stable UUIDv5 field ids. | Frontend metadata fragments read both fields, but reverse relation fields and morph metadata are not part of the seeded standard metadata. | Metadata fragments are non-empty and stable without adding non-queryable reverse fields; reverse field ids will be replaced once reverse metadata is seeded. |
| D-021 | Accepted | Seed reciprocal relation fields (`company.people`, `company.opportunities`, `person.pointOfContactForOpportunities`) and resolve relation target ids against real field metadata. | D-020 exposed synthesized reverse ids that were not queryable fields. | Forward relations now point at queryable reverse fields and reverse fields expose `ONE_TO_MANY`; fields for unseeded objects still fall back to synthesized ids. |
| D-022 | Accepted | Seed metadata for `taskTarget` and `noteTarget` without default views, and add `taskTargets`/`noteTargets` reciprocal fields to task, note, company, person and opportunity. | The target records already existed in GraphQL/REST but metadata boot did not describe them, leaving polymorphic reverse relations unresolved. | Metadata boot exposes seven objects and target relations resolve to real field ids; morph metadata is still not modelled because the storage keeps separate polymorphic columns. |
| D-023 | Accepted | Add the scalar `companyId` person filter to REST and GraphQL. | `PersonFilterInput` exposes both `companyId` and a nested `company` filter; the scalar id filter is cheap and unblocks common views. | `companyId` supports eq/neq/in/is; nested `company` field filters remain open. |
| D-024 | Accepted | Model `taskTarget`/`noteTarget` morph metadata (`target` head plus `targetCompany`/`targetOpportunity`/`targetPerson` sharing one `morphId`), populate `Field.morphRelations`, and seed `workspaceMember` metadata so `task.assigneeId`/`company.accountOwnerId` point at real reverse fields. Defer dynamic schema generation to Phase 5. | Metadata fragments expose morph relations and workspace-member reverse relations upstream; replacing the static schema with a metadata-generated one is a separate architectural change. | Metadata boot exposes eight objects; records keep separate polymorphic `*Id` columns, so morph metadata describes relations without changing storage. Role enforcement and dynamic schema generation remain open. |
| D-025 | Accepted | Add nested relation filters for people (`company`) and opportunities (`company`, `pointOfContact`) using SQL subqueries for people and preloaded relation maps for in-memory opportunity filtering; accept REST dot-path syntax (`company.name[eq]:...`). | The frontend view filters use nested relation predicates, and the REST parser already supports dotted field paths upstream. | Relation filters are covered by integration tests; nested relation ordering, `owner`/`accountOwner` filters and view-based paging remain open. |
| D-026 | Accepted | Honor `offsetForRecords` in REST groupBy and use the view's sorts as the default `orderByForRecords` when the caller omits an explicit order. | Upstream group-by paging applies the view's record order and offset per group. | Integration tests cover offset paging and view-sort ordering; GraphQL groupBy and nested relation ordering remain open. |
| D-027 | Accepted | Implement the frontend `Search` operation as a ranked union over the searchable standard objects (`person`, `company`, `opportunity`, `task`, `note`), with include/exclude object filters and cursor paging. Accept `ObjectRecordFilterInput` as an opaque scalar until its upstream shape is captured. | Search is a frontend root operation that was previously missing; the generated frontend document defines the result shape. | Ranked results and object filters are integration-tested; the search filter input and export/import remain open. |
| D-028 | Accepted | Flatten nested GraphQL `orderBy` inputs and support relation ordering for opportunity `company.*`/`pointOfContact.*` in GraphQL and REST, using preloaded relation maps. | Nested order inputs are the upstream shape, and the previous parser only understood flat JSON objects. | Relation ordering is integration-tested for opportunities; person/company relation ordering remains open. |
| D-029 | Accepted | Persist built-in roles in `core.roles`, expose them through `getRoles`/`getRole`/`getApiKeyRoles`, and implement `updateWorkspaceMemberRole`/`assignRoleToApiKey` with the legacy enum kept for authorization. | The frontend role settings need metadata-backed role ids and assignment; custom-role CRUD and permission enforcement are a separate design. | Built-in role assignment is integration-tested; custom roles, permission flags and enforcement remain open. |
| D-030 | Accepted | Implement custom role CRUD (`createOneRole`/`updateOneRole`/`deleteOneRole`) on `core.roles` while keeping built-in roles immutable. | The role settings page needs editable custom roles, but permission evaluation still relies on the legacy enum. | Custom roles are integration-tested for CRUD; assigning one authorizes as `MEMBER` until permission-flag enforcement lands. |
| D-031 | Accepted | Implement webhook settings CRUD (`webhooks`/`webhook`, `createWebhook`/`updateWebhook`/`deleteWebhook`) backed by `core.webhooks`, with admin-only writes. | The frontend settings surface needs webhook configuration before delivery workers exist. | CRUD is integration-tested; event emission/delivery and REST routes remain open. |
| D-032 | Accepted | Guard object/field metadata writes with the owner/admin role and cover the non-admin `FORBIDDEN` path in tests. | Phase 4's wrong-role acceptance needed an enforced write boundary; full permission-flag enforcement is a separate design. | Metadata writes are guarded; view/file/data permission flags remain open. |
